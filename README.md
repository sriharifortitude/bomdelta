# bomdelta

[![CI](https://github.com/sriharifortitude/bomdelta/actions/workflows/ci.yml/badge.svg)](https://github.com/sriharifortitude/bomdelta/actions/workflows/ci.yml)

Diff two CycloneDX SBOMs and flag the changes a release reviewer needs to
look at: a dependency that went *down* a version, an older duplicate copy
appearing next to a current one, and a licence that became more
restrictive. Rust, one dependency (`serde_json`), MIT.

## Why a diff

Generating an SBOM is one command in every ecosystem now, and the EU Cyber
Resilience Act (Regulation (EU) 2024/2847, Annex I Part II) makes drawing
one up an obligation for products sold in the EU. An SBOM on its own is a
list of seventy or seven hundred components. Nobody reviews that list on
every release. What a reviewer can review is what changed since the last
one.

A version-number diff isn't enough either. Here are two real npm releases
of the same app (`testdata/`, generated by npm itself from real registry
data, see `testdata/regenerate-npm-fixtures.sh`). The pull request changes
three lines of `package.json`: express pinned to 4.20.0 instead of 4.21.2,
tinymce 6 bumped to 7, and zod added.

What that output shows, checked against OSV.dev and the npm registry on
2026-09-27:

- **express 4.20.0 has no advisory of its own.** A scanner looking at the
  top-level package sees nothing wrong. The downgrade still pulls in
  `cookie` 0.6.0 (CVE-2024-47764) and `path-to-regexp` 0.1.10
  (CVE-2024-52798), both fixed in the versions they replace.
- **`send` 0.18.0 arrives as a second, older copy** next to 0.19.0, which
  stays. 0.18.0 carries CVE-2024-43799. Anything that compares only the
  newest version of each package reports `send` as unchanged.
  [ADR 1](docs/adr/0001-a-package-maps-to-a-set-of-versions.md) explains
  why packages map to sets of versions.
- **tinymce 7 is GPL-2.0-or-later; 6.8.5 was MIT.** It looks like a routine
  major bump, and it changes what shipping the product requires.

To be fair to vulnerability scanners: one run on the *after* lockfile (like
[vulnlock](https://github.com/sriharifortitude/vulnlock)) finds those
three CVEs too. bomdelta ties them to the pull request that introduced
them. It also flags a downgrade before anyone has published an advisory
for it, and flags licence changes, which vulnerability scanners don't
look at.

## Rules

| Rule | Severity | When |
| --- | --- | --- |
| `downgraded` | high | the version went down, or the highest of several copies did |
| `license-changed` | by where it landed | the declared licence changed: into strong copyleft or source-available is high, into weak copyleft or unrecognised is medium, a dropped declaration is medium, anything less restrictive is low |
| `older-copy-added` | medium | a version appears alongside a newer copy of the same package that was already there |
| `added` | by licence | new package: permissive is info, weak copyleft / unrecognised / no licence declared is medium, strong copyleft / source-available is high |
| `version-order-unknown` | low | the version changed but the two strings can't be ordered reliably (Maven qualifiers, Debian epochs); bomdelta says so rather than guessing a direction |
| `upgraded`, `relabelled`, `removed` | info | everything else that changed |

Licence classification is deliberately coarse. It answers "did the
obligations get heavier?", not "is this compatible with my licence?".
[ADR 2](docs/adr/0002-coarse-ordered-licence-categories.md) covers how
expressions are evaluated (`OR` takes the lighter side, `AND` the heavier),
why an unrecognised licence never counts as permissive, and why `BSL-1.0`
and `BUSL-1.1` get their own test.

## Usage

```bash
cargo install --git https://github.com/sriharifortitude/bomdelta --tag v0.1.0

bomdelta before.cdx.json after.cdx.json                        # terminal
bomdelta --format markdown base.cdx.json head.cdx.json         # for a PR comment
bomdelta --format json --fail-on medium old.json new.json      # for other tools
```

| Exit | Meaning |
| --- | --- |
| 0 | nothing at or above `--fail-on` (default `high`; `none` never fails) |
| 1 | at least one change is |
| 2 | usage error, unreadable file, not CycloneDX JSON, or an unsupported spec version |

In CI, generate an SBOM for the pull request's base and head and diff
them. A finding shows up once, on the pull request that introduces the
change, so there's no waiver file
([ADR 3](docs/adr/0003-no-waiver-file.md)): approving that pull request is
the acceptance. For a change that's intentional, either run the job as
non-blocking and post the `--format markdown` output as a comment, or
merge with an explicit override.

## What it doesn't do

- **No vulnerability lookup.** The CVEs above came from OSV.dev, checked
  separately. That's vulnlock's job; this tool reports the change.
- **CycloneDX JSON only**, spec 1.2 to 1.6. SPDX JSON is rejected with a
  message saying so, never read as an empty SBOM, because a diff against
  nothing would pass.
- **No licence compatibility verdicts**, and the SPDX table is short. An id
  it doesn't know is `unrecognised` (medium), never permissive.
- **Identity depends on purls.** Components without a purl fall back to
  group/name, which can't tell two ecosystems' same-named packages apart.
- **`file` components are skipped.** Some generators emit one per file,
  and a file listing is a different review.
- **Not tested against** syft, cdxgen, cargo-cyclonedx or Maven plugin
  output. The fixtures are npm's own. The parser only reads fields the
  CycloneDX schema defines, but those generators' quirks haven't been
  exercised.

## Testing

```bash
cargo test    # 51 unit tests (purl identity, version order incl. the semver
              # spec's own precedence chain, licence expressions, set diff)
              # + 7 end-to-end tests running the binary on the real npm SBOMs
```

CI also runs clippy with warnings as errors, checks formatting, builds on
the declared minimum Rust version (1.77) as well as stable, and fails if
the output block above no longer matches what the binary prints.
